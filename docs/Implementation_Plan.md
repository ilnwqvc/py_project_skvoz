## Схема данных

`raw` - исходный JSON-ответ API, без правок.

`normalized` - очищенная таблица после `transform`. Одна строка здесь - одно часовое наблюдение по городу.

`mart` - дневная витрина для анализа. В ней уже собраны основные показатели: средняя температура, сумма осадков, максимум ветра и количество дождливых часов.

## Зачем разделены слои

Разделение простое:
- `raw` нужен, чтобы всегда можно было вернуться к исходному ответу API
- `normalized` нужен для чистых почасовых данных
- `mart` нужен, чтобы не считать дневные метрики каждый раз заново

Если держать все в одном файле, сложнее искать ошибки и проверять, на каком этапе данные испортились.

## Full и incremental режимы

`full` полностью пересобирает данные за период из конфига. Старые `normalized` и `mart` при этом перезаписываются.

`incremental` берет только новые данные после последнего `watermark`. Дубли отсекаются по бизнес-ключу.

Состояние пайплайна лежит в `data/state.json`. Там хранятся `last_watermark` и `last_run`.

Бизнес-ключ для `normalized` - пара `city_id` и `ts`. По ним можно однозначно понять, к какому городу и часу относится запись.

`watermark` обновляется только после успешного завершения пайплайна. Так меньше риск потерять данные, если загрузка или сборка витрины упали в середине.
