# Контракт данных

Версия контракта: `0.3`

Проект / вариант: `06`, погодный архив по Токио  
Источник: `Open-Meteo Archive API`  
Основная сущность: `JP_TYO` / Токио  
Часовой пояс: `Asia/Tokyo`  
Интерпретация времени:
- временные метки из API приходят в локальном времени Токио
- `normalized.ts` хранит локальный timestamp в `Asia/Tokyo`
- `mart.date` - это локальная календарная дата, полученная из `normalized.ts`

Гранулярность слоев:
- `normalized`: 1 строка = 1 почасовое погодное наблюдение по одному городу
- `mart`: 1 строка = 1 день по одному городу

Зачем нужен этот контракт:
- фиксирует смысл колонок, единицы измерения и правила nullable
- явно описывает время и часовой пояс
- снижает риск тихого расхождения между кодом, данными и аналитикой

## Правила именования и единиц

- Все физические имена колонок пишутся в `snake_case`.
- Поля времени должны иметь однозначный смысл:
  - `ts` = timestamp
  - `date` = локальная календарная дата
- Единицы измерения должны быть указаны в контракте, даже если они кажутся очевидными.
- Неоднозначные имена вроде `value`, `metric1`, `data` не допускаются.
- KPI-поля в `mart` должны отражать бизнес-смысл:
  - `T_mean` = средняя температура
  - `P_sum` = сумма осадков
  - `wind_max` = максимальная скорость ветра
  - `rainy_hours` = количество дождливых часов
- Если единицы не зашиты в имя колонки, они должны быть явно зафиксированы в контракте и словаре данных.
- Для всех временных полей обязательно нужно документировать timezone, чтобы не было разной трактовки у разных людей.

## Слой normalized

Назначение слоя:
Хранение очищенных почасовых наблюдений после `transform` и до агрегации в `mart`.

Бизнес-ключ:
`(city_id, ts)`

Схема:

| column_name | dtype | nullable | unit | description |
|-------------|-------|----------|------|-------------|
| ts | timestamp | no | локальная дата-время, `Asia/Tokyo` | Временная метка почасового погодного наблюдения. Получается из поля `hourly.time` API. |
| temperature_2m | float | yes | `°C` | Температура воздуха на высоте 2 метров в конкретный час. |
| relative_humidity_2m | float | yes | `%` | Относительная влажность на высоте 2 метров в конкретный час. |
| precipitation | float | yes | `mm` | Количество осадков за конкретный час. |
| wind_speed_10m | float | yes | `km/h` | Скорость ветра на высоте 10 метров в конкретный час. |
| city_id | string | no | идентификатор | Идентификатор города из конфига. В текущем проекте всегда `JP_TYO`. |

Примечания:
- `ts` приводится в коде через `pd.to_datetime(...)`.
- Числовые погодные колонки приводятся через `pd.to_numeric(..., errors="coerce")`.
- Сейчас источник только по одному городу, но `city_id` сохранен для стабильного бизнес-ключа и возможного расширения.

## Слой mart

Назначение слоя:
Дневная аналитическая витрина для быстрого анализа и визуализаций.

Бизнес-ключ:
`(date, city_id)`

Схема:

| column_name | dtype | nullable | unit | description |
|-------------|-------|----------|------|-------------|
| date | date | no | локальная дата, `Asia/Tokyo` | Календарная дата, полученная из `normalized.ts` в локальном времени Токио. |
| city_id | string | no | идентификатор | Идентификатор города. В текущем проекте это `JP_TYO`. |
| T_mean | float | yes | `°C` | Средняя температура за день. Считается как среднее по всем часовым значениям `temperature_2m` за один день и один город. |
| P_sum | float | yes | `mm/day` | Сумма осадков за день. Считается как сумма всех часовых значений `precipitation` за один день и один город. |
| wind_max | float | yes | `km/h` | Максимальная скорость ветра за день. Считается как максимум по часовым значениям `wind_speed_10m` за один день и один город. |
| rainy_hours | integer | yes | `hours` | Количество часов в сутках, где `precipitation > 0`. |

Как считаются метрики:
- `T_mean = AVG(temperature_2m)` по `date, city_id`
- `P_sum = SUM(precipitation)` по `date, city_id`
- `wind_max = MAX(wind_speed_10m)` по `date, city_id`
- `rainy_hours = COUNT(hour where precipitation > 0)` по `date, city_id`

Почему здесь важны единицы измерения:
- `P_sum` - это сумма, и она зависит от выбранной гранулярности. Если перепутать `mm` за час и `mm` за день, метрика будет интерпретироваться неправильно.
- `wind_max` использует ту же единицу, что и почасовой источник, поэтому его нельзя напрямую сравнивать с данными в м/с без пересчета.
- `T_mean` - это среднее значение, а не мгновенная температура в конкретный момент.

## Контроль контракта и DQ

Текущие точки контроля в пайплайне:
- после `transform` для `normalized`
- после `build_mart` для `mart`
- до `load_to_db()`

Что сейчас проверяется автоматически:
- ожидаемый набор колонок относительно схемы контракта
- непустота таблиц
- отсутствие NULL в критичных полях
- уникальность бизнес-ключей
- приводимость временных колонок к datetime
- числовые диапазоны
- допустимые значения
- монотонность timestamp внутри одного города

Примеры соответствия "контракт ↔ код":
- `normalized.ts` создается в [transform.py](/d:/progscode_2semestr/python_programming/src/transform.py:15) через `pd.to_datetime(df["ts"])`
- `mart.T_mean` создается в [transform.py](/d:/progscode_2semestr/python_programming/src/transform.py:54) как дневное среднее по `temperature_2m`
- `mart.P_sum` создается в [transform.py](/d:/progscode_2semestr/python_programming/src/transform.py:55) как дневная сумма `precipitation`

## Кратко по DQ-правилам

DQ-проверки описаны в `configs/variant_06.yml` и исполняются модулем `src/dq.py`.

### Normalized

| rule | check | severity | violation |
|------|-------|----------|-----------|
| normalized_expected_columns | точное совпадение набора колонок | FAIL | отсутствует нужная колонка или появилась лишняя относительно контракта |
| normalized_not_empty | таблица не пустая | FAIL | в слое нет строк |
| normalized_not_null_keys | `ts`, `city_id` не NULL | FAIL | хотя бы одно ключевое поле пустое |
| normalized_unique_business_key | уникальность `(city_id, ts)` | FAIL | найден дубль по бизнес-ключу |
| normalized_ts_is_datetime | `ts` приводится к datetime | FAIL | есть непарсимые значения |
| normalized_ts_monotonic | `ts` возрастает внутри `city_id` | WARNING | нарушен порядок времени |
| normalized_temperature_range | `temperature_2m` в диапазоне `[-80, 60]` | FAIL | температура вне допустимого диапазона |
| normalized_humidity_range | `relative_humidity_2m` в диапазоне `[0, 100]` | FAIL | влажность вне допустимого диапазона |
| normalized_precipitation_non_negative | `precipitation >= 0` | FAIL | отрицательные осадки |
| normalized_city_allowed | `city_id` входит в допустимый список | WARNING | встретился неожиданный идентификатор города |

### Mart

| rule | check | severity | violation |
|------|-------|----------|-----------|
| mart_expected_columns | точное совпадение набора колонок | FAIL | отсутствует нужная колонка или появилась лишняя относительно контракта |
| mart_not_empty | таблица не пустая | FAIL | в витрине нет строк |
| mart_not_null_keys | `date`, `city_id` не NULL | FAIL | пустое ключевое поле |
| mart_unique_business_key | уникальность `(date, city_id)` | FAIL | найден дубль по дню и городу |
| mart_date_is_datetime | `date` приводится к datetime | FAIL | дата не парсится |
| mart_precipitation_non_negative | `P_sum >= 0` | FAIL | отрицательная сумма осадков за день |
| mart_rainy_hours_range | `rainy_hours` в диапазоне `[0, 24]` | WARNING | невозможное количество дождливых часов |
| mart_wind_non_negative | `wind_max >= 0` | WARNING | отрицательная максимальная скорость ветра |
