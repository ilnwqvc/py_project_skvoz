# Week 13 ML

Здесь взят простой сценарий A: классификация дождливого часа.

## Что предсказываем

Цель:
- предсказать, будет ли час дождливым

Target:
- `is_rainy_hour = 1`, если `precipitation > 0`

Признаки:
- `temperature_2m`
- `relative_humidity_2m`
- `wind_speed_10m`

Что специально не брали:
- `precipitation` не включал в `X`, потому что это и есть источник target, иначе была бы прямая утечка
- `ts` не использовал как числовой признак, чтобы не городить лишнюю историю на маленьких данных

## Как делил данные

Так как данные временные, split только по времени:
- train: первые 80% строк
- test: последние 20% строк

То есть модель учится на прошлом и проверяется на будущем.

## Baseline и модель

Baseline:
- `DummyClassifier(strategy="most_frequent")`

Модель:
- `LogisticRegression`

## Метрики на test

Baseline:
- Accuracy: `0.8214`
- Precision: `0.0000`
- Recall: `0.0000`
- F1: `0.0000`

LogisticRegression:
- Accuracy: `0.7214`
- Precision: `0.3833`
- Recall: `0.9200`
- F1: `0.5412`

## Как это интерпретировать

По accuracy baseline выше, но это обманчиво, потому что он почти всегда говорит "дождя нет".  
Для такой задачи важнее то, что baseline вообще не находит дождливые часы: у него `Recall = 0` и `F1 = 0`.

Простая логистическая регрессия хуже по accuracy, зато:
- реально находит дождливые часы
- дает высокий recall
- заметно лучше baseline по F1

## Вывод

Если цель просто максимизировать accuracy, то такая модель не нужна.  
Если цель — не пропускать дождливые часы, то даже простая модель уже полезнее baseline.

Честный вывод такой:
- как минимальный аналитический baseline это нормально
- модель что-то ловит и не сводится к угадыванию самого частого класса
- но данных мало, поэтому делать сильные выводы рано

Что можно улучшить дальше:
- добавить лаговые признаки по погоде
- попробовать более аккуратный подбор порога
- проверить еще одну простую модель
- накопить больше данных по времени
